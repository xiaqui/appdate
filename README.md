# Release Store — 個人用 Android アプリストア

GitHub Releasesを配布元として、登録した複数のpublic/privateリポジトリのAPKを端末で確認・更新する試作です。Android 6〜10（API 23〜29）が主要対象で、基盤アプリとしてAndroid 14（API 34）までCI互換性を確認します。

0.9.2検収版では、承認したForgejo接続先のRelease APKも同じアプリ行へ統合できます。アプリはAPK実体のpackageNameと署名、配布元はprovider・正規化サーバーURL・repository IDで区別します。repo名だけでは統合しません。同じversionCodeの独立ビルドが競合した場合は、配布元とSHA-256を確認してその版だけの候補を明示選択できます。通常の優先順位は変えず、新版や内容変更では選択を失効します。

## 初回設定

1. [検収用プレリリース](https://github.com/xiaqui/appdate/releases)で、目的の `store-preview-<SHA>` にある **ReleaseStore-preview.apk** をログイン済みブラウザから開きます。ストア版のIDは `jp.xiaqui.artifact.store.preview`。旧Installer版と並行導入でき、旧版の保存データは旧版から開けます。
2. 起動して「リポジトリを登録」に `owner/repo` またはGitHub URLを貼り付けます。「最新の対象にプレリリースも含める」は登録ごとに変更できます。
3. メニューの「設定」でContents読み取り権限の共通PATを登録します。GitHub側で許可した複数repo・新規repoに適用されます。公開repoは匿名を優先し、アクセス拒否・制限時に共通PATを使用します。「個別PATの設定・再認証」はそのrepoだけの例外です。個別PAT解除は共通PATへ戻り、共通PAT解除は個別設定を保持します。どちらもAndroid Keystoreの鍵で暗号化し、バックアップ対象外に保存。鍵喪失時は該当設定を再入力してください。0.4.1のメモリにだけあったPATは初回登録が必要です。

## 更新と過去版

トップ画面の「一括更新確認」、または個別repoの「更新を確認」を押します。下書きを除くAPK付きReleaseを公開日時順に表示します。プレリリースを除く設定では正式版だけが対象です。取得日時とエラーを表示し、通信失敗後も最後に取得した履歴を利用できます。

トップはアプリ名・導入版 → 最新版・更新状態をまとめたタップ可能な行です。「前回」は最後の成功時点の版情報です。一括確認は成功・更新候補・同一版・失敗のrepo数を表示します。中断した確認は未完了として残ります。行をタップすると確認日時・最終成功日時、認証・再試行、Release履歴と保存操作が開きます。Asset詳細でID・提供されているSHA-256を確認できます。登録がゼロでもメニューから保存済みAPKを開けます。

404の詳細にはRelease一覧／タグ／Asset本体／転送先と、該当リクエストの認証有無を表示します。公開repoに公開済みReleaseがないと一覧は空で成功する一方、存在しないタグ・Assetや閲覧権限のないprivate repoは404になり得ます。repo名、公開範囲、選択した対象、PATのrepo指定とContents権限を確認してください。トークン・完全URLは診断に記録しません。

最新Releaseの未解析APKは、更新確認1回につき最大4件を一時取得してpackageName・アプリ名・versionCode・署名を調べます。通信量はAPKサイズに依存します。同じAssetの検査結果は次回も利用します。残りの候補と過去版は「APK情報を確認」で個別に解析できます。複数APKは明示的に選択してください。ABI・split構成の完全な判定および分割APKの一括導入は対象外です。

「保存してインストール確認へ」で選択したAPKを取得・検査し、永続保存します。確認画面で「標準インストーラで開く」を押してください。Android 6はPackageInstaller.Session、7以降はFileProviderを使用。Android 8以降の初回は「この提供元を許可」を設定し、戻ってもう一度押します。6/7はOSの提供元不明アプリ設定に従います。

更新状態は実APKと端末のpackageName、数値のversionCode、署名証明書から判定します。現署名が違う場合は「署名不一致の可能性」と表示します。署名ローテーション、ABI、SDK要件など、導入可否の最終判定はOSに従います。旧版の通常の上書きは制限されます。手動でアンインストールすると対象アプリのデータが消えます。ストアにアンインストール操作はありません。自動ロールバックや設定移行はPhase 2です。

## 保存・障害時

複数配布元では、最大versionCodeを確認した後、同一版なら利用者が保存した優先順位を使います。同じversionCodeでAPKのSHA-256が不明または不一致なら自動取得を停止します。優先元に障害がある場合も、同じSHA-256を確認済みの承認済み予備元だけを使用し、設定順位は書き換えません。復旧後は次回確認で元の順位へ戻ります。配布元を解除しても履歴と保存APKは保持します。

保存先はアプリ専用の `files/apks/`。1 APKは128 MiBまで、1パッケージ3世代・全体24件・512 MiBまで保持します。上限時は「保存したAPK」から削除対象を選びます。自動削除はありません。ストアの保存履歴にはrepo、タグ、Asset識別子、packageName、バージョン、保存日時を記録します。インストールのキャンセル後も同じAPKを再度開けます。登録削除はAPKを保持します。

403/429の利用制限は時間をおいて再試行、401/404ではrepo・権限・期限を確認して再認証してください。API認証は最初の api.github.com 宛に限定し、署名付き転送先へのAuthorizationを外します。GitHub Mobileのセッションは使用しません。1リポジトリ3,000 Release、1 Release 1,000 Assetまで。端末ストレージ不足・破損APK・署名不一致は各段階で表示します。

従来のRelease共有、ファイル選択・ZIP抽出は補助機能です。アプリが作ったZIPと一時コピーは処理後に削除し、選択APKと利用者の元ファイルを保持します。

## 配送・署名

GitHub Actionsで単体テスト、lint、API 23/29/34試験、APKの署名・minSdkを検査し、SHA単位の検収用プレリリースへ添付して再取得・バイト照合します。verifyが署名済み本体APKと計装APKを一度だけ生成し、source SHA、ソースidentity、applicationId、版、証明書、SHA-256をmanifestに記録します。deviceはGradleで本体を再ビルドせず、そのAPK自体で初回導入・旧版上書き・データ保持を検証します。CIだけの変更では、成功済みrunのbundleを同一ソース・署名・hash検証後に再利用できます。さらに同じsource runでAPI 23/29/34が実際に成功し、deviceスクリプト・baseline・matrix・runner設定・bundle検査が同一の場合だけ、そのdevice結果も再利用してエミュレータ再実行を省略します。明示的なforce/full matrix、条件変更、不一致・期限切れ・取得不能では再実行または安全側に停止します。Actions Artifactは7日間のCI内受け渡し用で、Releaseをキャッシュ代わりに増やしません。同じタグのAssetを別バイナリで上書きしません。

配送は既存の固定鍵・alias `xiaqui` を必須とし、0.4.1の証明書SHA-256とも照合します。Secrets未設定や指紋不一致なら配送は失敗します。同一IDでも以前の一時debug鍵ビルドとは署名が異なります。

PR #6の0.8.1/code 13検収版は [`store-preview-fa230d039ad8`](https://github.com/xiaqui/appdate/releases/tag/store-preview-fa230d039ad8) です。APK sourceは`cd92f9a5e7b30c10c0c4ca863fa5aa857f2238ad`、APK SHA-256は`28cc3ebe4dc65bd38928652cc6c6e53f9cc7c65888266c52ea0b6bc7d752d864`、固定証明書SHA-256は`dcfd2c8122274ec4148473c96b1853989c8d22e58e445d6ec4889ad5b34dffb2`です。API 23/29/34で同一APKの導入・計装・0.4.2上書き・データ保持を確認済みで、物理端末検収前にはマージしません。

## 実機検収

- 通常のアプリ一覧・詳細・認証設定画面ではスクリーンショットを撮影できることを確認。共通PAT／個別PATの入力ダイアログを開いている間だけ撮影不可となり、閉じた後は再び通常画面を撮影できることを確認する。PAT文字列をスクリーンショットやログへ残さない。
- 公開・非公開repoを登録し、個別・一括更新、編集・削除、通信を切った状態のキャッシュ、プロセス終了後の認証維持と明示解除を確認。
- 単一・複数APKのアプリ名、packageName、versionCode、導入済み版を確認。プレリリース表示を切り替え、過去版を選択。
- 旧版・署名違いの表示を確認。Android 6/7と8以降でOS確認画面を開き、キャンセル後の保存、再起動後の再試行を確認。

### Z4T（Android 7）・Z3TC（Android 6）のTLS再検収

1. 0.9.2（versionCode 19）を既存のAppDateへ上書きします。登録、認証、保存済みAPK、更新設定が残っていることを確認します。
2. 症状が出たWi-Fiにつなぎ、起動時の自動更新確認とWi-Fi接続時のAPK自動取得をONにしてAppDateを開き直します。処理完了後、repo詳細の「今回の確認」と「自動／一括取得」を記録します。
3. 同じ回線・同じReleaseのAPK詳細を開き、個別の再解析を実行します。Z4Tと、ISRG Root X1を手動導入していないZ3TCの双方で成功することを確認します。
4. TLS失敗が残る場合は、保留行の `active`、`internet`、`validated`、`otherWifi` と、表示された通信段階・エラー種別を控えます。PAT、署名付きURL、SSID、IPアドレスは記録しません。
5. 端末に既にあるCAは削除せず、AppDate側の互換実装だけで再検収します。信頼境界とfingerprintは `docs/TLS_COMPATIBILITY_JA.md` を参照してください。

JDK 17、Gradle 8.9、Android SDK 35。ローカル検証は `gradle testDebugUnitTest lintDebug assembleDebug`、端末試験は `gradle connectedDebugAndroidTest`。エミュレータの自動試験と物理端末の検収は区別します。

Release・更新確認・保存日時は表示時に端末のタイムゾーンで yyyy/MM/dd HH:mm に変換します。保存したAPKはメニューの一つの画面で扱い、端末ファイルとGitHub取得分の出所を表示します。記録のない旧APKは「旧保存分」と表示し、ファイル欠落時も履歴を保持します。APK詳細では実ファイルの署名を確認できます。別applicationIdの旧Installerはアプリ専用領域が異なるため、自動移行の対象外です。

## 正式Release

実機検収済みのAPKを再ビルドせず昇格します。対象の版・元SHA・サイズ・APKと証明書の指紋は `.github/release/accepted.json` を参照してください。mainの **Promote accepted APK** でpublishを明示するか、配送設定更新のマージコミットに `[publish-stable]` を指定します。PRでは読み取り検証のみ行います。既存の公開Assetを差し替えず、ドラフトから再取得してビルド済みAPKとの一致を確認してから正式公開します。

## 自動更新確認・通知（0.8.3検収版）

設定の「自動更新」には、互いに独立した3項目があります。起動時の自動更新確認は初期値ON、約6時間ごとのバックグラウンド確認は初期値OFF、Wi-Fi接続時のAPK自動取得は初期値ONです。定期確認をOFFにするとOSの予約を解除します。起動時確認や自動取得をOFFにしても、手動の一括確認・個別確認・一括ダウンロードは利用できます。旧版で「自動処理を一時停止」していた場合は、明示した停止を守って3項目ともOFFへ移行し、旧版で自動取得だけをOFFにしていた場合もその値を保持します。

起動時確認がONなら、新規起動とアプリ外からの復帰ごとに確認します。画面内の再描画やダイアログ操作だけでは再実行せず、処理中に復帰要求が重なった場合は最新の要求を失わず順番に処理します。トップの集計は自動・手動で同じ「成功／更新／同一／失敗」定義を使い、確認方法・確認時刻・確認中／完了／失敗／未完了を表示します。確認中にプロセスが終了した記録は次回起動時に未完了へ直し、失敗時も前回の成功情報と登録・履歴・保存APKを保持します。定期確認はDoze・省電力・強制停止等で遅れる場合があります。自動確認中のAPK解析と自動取得は、自動取得ONかつWi-Fi接続中だけ許可し、転送中も接続・設定を再確認します。最新ReleaseのAPKが1個で、実体のpackageName・versionCode・署名・対応OSを検査でき、端末の導入済みアプリに対する互換更新と確認できた場合だけ保存します。モバイル通信や自動取得OFFで黙ってAPKを取得しません。複数APK・署名違い・非対応または不明OSは自動保存しません。

「未取得の更新を一括ダウンロード」は検査済み更新候補に対する手動操作です。Wi-Fi以外では最大通信量を表示し、その回だけの明示許可を求めます。準備完了通知は、1件ならAPK確認画面、複数なら保存APK一覧を開きます。必ず利用者が「標準インストーラで開く」を押し、OSの最終確認を行います。通知を消してもAPKは削除しません。

保存上限は従来どおり単体128 MiB、1パッケージ3世代、全24件・512 MiBです。上限が迫った際は、自動取得かつ導入済みの古いAPKだけを整理候補にします。手動保存・取り込み、インストール待ち、現在開いているAPK、唯一の互換復旧候補、履歴は保護します。安全な対象がなければ取得を保留します。

実機では、既存版へ上書きして登録・共通/個別PAT・Release履歴・保存APKが残ること、3スイッチが再起動後も保持されること、定期OFFで予約されずONで予約されること、Wi-Fi自動取得ON/OFFとモバイル通信での抑止、通知からOS確認画面まで、手動確認・手動取得を確認してください。ソース・CIのAPI 23/29試験と、物理端末でのDoze・OEM省電力・実回線・実PAT検収は区別します。

## 共通PATからAPK配布repoを自動登録（0.7.1検収版）

共通PATの保存・変更時と「repoを再取得」で、GitHubの列挙APIが返した未登録repoを確認します。Public/Privateを問わず、公開済みReleaseの全ページに、アップロード済みでサイズがある `.apk` assetが一つ以上見つかったrepoだけを追加します。最新ReleaseにAPKがなくても、過去のReleaseにあれば対象です。GitHub Actions Artifact、draft Release、ZIP等は対象にしません。

共通PATの保存・変更では、自動追加に成功したrepoだけを対象に、既存の更新確認処理でRelease情報・APKメタデータ・インストール状態を続けて確認し、完了後にアプリ一覧へ戻ります。「repoを再取得」でも新規追加分だけを初回確認し、既存登録の一括確認は従来の「一括更新確認」で行います。repo登録と初回確認は別々に保存するため、一部の確認に失敗してもPAT、追加済み登録、履歴、保存APKは取り消しません。失敗した行は未確認・再試行可能な状態で残ります。確認時の一時APK取得は既存の更新確認と同じで、保存やインストールは自動実行しません。

Release履歴を最後まで確認してAPKがないrepoは追加しません。401/403/404/429、通信断、API制限、途中ページの失敗は「配布なし」と断定せず判定保留にし、再取得できます。結果には取得、APK履歴確認、追加、既存、配布なし、判定保留の件数と先頭の理由を表示します。既存登録はReleaseの有無にかかわらず保持し、自動削除しません。個別PAT、取得履歴、解析情報、保存APKも変更しません。

列挙したGitHub IDは改名保護と照合します。同名の別IDや過去の改名記録との衝突は上書きせず保留します。既存IDが同じで現在名だけが異なる場合も勝手に登録を移動せず、登録編集から安全な改名移行を行います。手動登録は従来どおりAPK配布履歴がないrepoにも使用できます。

実機では、まず既存データを消さずに上書きし、登録・個別PAT・Release履歴・保存APKが保持されること、PAT変更後に新規追加分だけが初回確認されトップへ戻ることを確認してください。続いてアプリデータを消去し、共通PAT登録からAPK配布repoの自動追加、初回更新確認、トップ表示まで手操作なしで完了することを確認します。過去ReleaseだけにAPKがあるrepo、未配布から配布開始後の再取得、通信失敗後の判定保留と再試行も対象です。APIの列挙範囲と組織承認は実PAT・実端末での確認が必要です。

## リポジトリ改名の移行（0.7.0検収版）

アプリ詳細の「登録を編集」で新しいowner/repoを入力します。GitHub上のrepo自体は変更しません。旧IDがある場合は安定IDのAPI、未記録の場合は旧URL（GitHub API内の転送のみ）からIDを確認し、新URLのID・現在名と照合します。ID未記録で履歴がある場合は保存済みの先頭Release IDも移転先で照合します。ネットワークとMetadata権限、履歴照合にはContents権限が必要です。

成功時は全履歴・解析済みAPK・取得日時・取得エラー・表示設定を保持し、変更したプレリリース設定だけを反映。個別PATは新名のKeystore鍵へ暗号化保存・復号確認した後に旧認証を片付けます。共通PATは変更しません。登録と出所対応と認証完了待ち記録は一回のSharedPreferences commitで保存します。認証コピー途中なら旧登録・旧認証が残り、登録切替後なら新登録と完了待ち記録が残ります。「登録を編集→保存」で完了を再試行できます。新認証が欠損した場合は旧認証から再コピーします。新旧PATが競合した場合は、新名称の個別PATを明示解除して同操作を行うと旧PATを回復します。登録切替前の中断で変更先が未登録の場合は、登録編集で変更先名を入力し「中断復旧：未登録の変更先PATを解除」を確認してから保存を再試行します。旧認証は保持し、登録済み変更先の認証はこの操作では解除しません。切替後に旧鍵だけを失った場合は、検証済みの新認証が読めれば完了できます。新旧とも復号できない場合は現在名の個別PATを再入力して保存を再試行します。

保存APKの実体・hash・署名・package/versionと台帳原文は変更しません。原子的に保存した旧名→現在名対応で出所表示と再利用参照を解決します。改名後の登録を削除しても、この対応とIDは古いAPKの由来を保護するため残ります。名前が別IDに再利用された場合は追加・移行を保留します。履歴Release削除、ID不明、404/権限不足、通信断、別ID、変更先登録済みは推測統合せず双方を保持します。同一IDの重複登録でも自動統合はしません。片方の履歴が不要と利用者が判断した場合だけ登録削除（APKは保持）後に再試行してください。

PR #4の自動登録は未統合です。統合時は `Catalog.registeredIdentity(id, name)` と検証済みID付き `register` を列挙結果の追加前に使用する必要があります。この版だけで未統合PRの動作まで保証しません。旧名予約・ID一致・再列挙相当の重複防止を試験します。PR #6の自動更新や別branchの外部Intent拡張も含めません。
