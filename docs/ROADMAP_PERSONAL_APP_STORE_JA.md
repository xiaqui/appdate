# Artifact 将来構想：個人用 Android アプリストアと配布基盤

作成日：2026-11-12

> **位置づけ：構想資料。今回の実装指示ではない。**
> Phase 1 の実装範囲・完了条件はルートの `TASK.md` を正本とする。本書のPhase 2以降を、今回のPRへ無断で追加しない。

## 背景と目的

複数の自作AndroidアプリをWorkとGitHub Actionsで並行開発すると、APK生成速度に対して、端末への配送・インストールが追いつかない。GitHub ActionsのArtifactを開き、ZIPをダウンロード・解凍し、APKを探してインストールする作業をなくしたい。

目標は**開発者が普段GitHub ActionsやArtifactを意識せず、端末上の専用アプリから更新・旧版確認・復帰を行えること**。GitHub Releasesを配布元とし、専用サーバーやF-Droid互換リポジトリの構築を前提にしない。

想定利用者は本人、対象は主にAndroid 6〜10の複数実機。一般公開ストアや他者向け配布基盤を作ることが目的ではない。

## 全体像

1. Workが各アプリを実装・テストしてPRを作る。
2. GitHub Actionsが検収用APKをビルドし、GitHub Release（必要ならプレリリース）へ登録する。
3. Artifactアプリが登録repoのReleaseとAPKを一覧・更新確認する。
4. APKを取得・保存し、OS標準インストーラを起動する。
5. 開発者が実機で確認する。GitHub Actions画面やZIPを日常的に操作しない。

Releaseへの自動配布は**各プロジェクト側の段階的な移行作業**。ArtifactアプリのPhase 1実装だけで既存全repoの配布設定が自動的に変わるわけではない。

## Phase 1：アプリストアとしての最小完成形

詳細は `TASK.md` に従う。

- 複数GitHub repoの登録・編集・削除、public/privateの認証。
- 正式Release・プレリリース・過去ReleaseからAPK Assetを取得。
- 端末の導入済みAPKとversionCode等を比較し、更新候補を表示。
- APKを端末内に保持し、OS標準インストーラの確認画面まで案内。
- 旧版APKの選択・保存。Androidの署名・ダウングレード制約を明示。
- エラー復旧、キャッシュ、APK保存容量管理、Android 6〜10の互換性。

「自動取得・インストーラ起動」と「ユーザー確認不要の無人インストール」は別物。後者はPhase 1に含めない。

## Phase 2：一時ロールバックと元の設定への復帰

### 真の利用目的

ダウングレードは主に**新旧版の動作差を調べるための一時検証**。旧版に新版の設定を移植する必要はない。**新版へ戻した際に、元の新版の設定が復活すれば十分**。

### 想定フロー

1. 現在のAPK（versionCode・署名・取得元Release・ビルドSHA）を確保する。
2. 現行アプリから対応可能な設定をエクスポートし、Artifact側で安全に退避する。
3. 退避の成否と復元可能範囲を表示。失敗時はデータ保護を保証せず、明示的な同意なしにアンインストールしない。
4. 必要なら現行版をアンインストールし、選択した旧版APKをインストールする。OS確認画面は維持。
5. 旧版で動作確認する。**旧版に新版の設定を取り込ませない**。
6. Artifactの「元の版に戻す」で元のAPKを再インストールする。
7. 対応アプリのインポート機能を通じて退避設定を復元し、復元結果を報告する。
8. 復元完了を確認するまで、元のAPKとバックアップを削除しない。

### 技術的な制約と設計原則

- Androidの通常アプリは他アプリのprivate dataを自由に読めない。Artifact単体で既存アプリの設定を完全バックアップできるとは扱わない。
- 各自作アプリに、明示的なエクスポート／インポートAPIやファイル連携を用意する構想。対象アプリ側が**現在版でエクスポート可能、戻した版でインポート可能**であることが前提。
- インポート時は項目単位の妥当性検証を行い、未知項目や不整合項目を安全に無視する。暗黙の上書きやデータ破壊を避ける。
- バックアップはアプリ別・packageName別・版別・日時別に管理し、暗号化・アクセス制御・保存期限・容量上限を設ける。機密情報や認証トークンは原則エクスポート対象から除外。
- 一時ロールバックの進行状態を永続化し、途中キャンセル、再起動、インストール失敗、署名不一致、元APK消失から再開・復旧できるようにする。
- **設定の退避・復元非対応アプリ**では「元の設定を復活できない」と明示し、APKのみの一時ロールバックを選択制にする。
- 旧版を試した後の設定は基本的に破棄してよい。目的は元の新版状態への復帰であり、旧版との双方向同期ではない。

### 事前に必要な共通仕様

将来、Overlayなど設定が多い自作アプリから順に、エクスポート／インポートの共通契約を設計する。最初から全repoを変更しない。互換性テストはバックアップの生成元と復元先が同じ新版であるケースを優先する。

## Phase 3候補：導入作業のさらなる省力化

- ADB経由の複数端末一括インストール（PC補助ツール）。端末の接続・認可が必要。
- Device Owner等による管理端末向け無人インストールの調査。ただし常用端末への強制導入や初期化を前提としない。
- 端末ごとの導入版・更新状況の見える化。
- 検収メモやテスト結果との紐付けは、インストールの省力化より優先しない。

通常権限のAndroidアプリだけで、インストール確認や署名・ダウングレード制約を回避できると主張しない。

## Release運用の構想

- 各repoのCIはテストとAPK生成を行い、配布用APKをRelease Assetに置く。PR由来の未信頼コードに書き込みトークンを無条件で渡さない。
- 正式版と検収用プレリリースを区別する。タグ、Asset命名、同一タグの更新可否、保持世代数を標準化する。
- 同じpackageNameの上書き更新には署名の継続性が必要。CIの一時debug鍵を毎回生成する方式では継続更新できないため、配布鍵の保管・利用方式を別途設計する。
- APKにversionCode、ビルドSHA、署名情報を紐付け、端末側で識別可能にする。Releaseタグ文字列だけを更新判定の根拠にしない。
- private repoのRelease取得には認証が必要。最小権限、秘密情報の非表示、期限切れ時の再認証を考慮する。
- 過去版を残すことで一時ロールバックを容易にする。Assetの差し替えによる追跡不能を避けるため、ビルド同一性を記録する。

## 非目標・判断の優先順位

1. **最優先：** Android端末へのAPK配送・インストールの手間を減らす。
2. 次点：過去版を選びやすくし、新版へ元の設定ごと戻せるようにする。
3. 将来：複数端末管理、検収支援、ADB連携。
4. 対象外：一般向けアプリマーケット、任意アプリの内部データ強制取得、OSの安全確認回避。
