# TASK — リポジトリ改名時の登録・履歴・認証の安全な移行

作成: 2026-11-16
状態: Work向けの次期独立タスク。未実装。現行の自動更新PR #6やPAT自動登録PR #4とは混ぜない。
対象: Release Store（現在のrepo: `xiaqui/artifact`）、Android 6〜10。

## 目的と背景

GitHub上のリポジトリ名が `xiaqui/artifact` から将来 `xiaqui/release-store` に変更されても、端末のRelease Store内で登録名を編集するだけで既存のRelease履歴、APK解析結果、更新状態、個別認証および保存済みAPKへの参照を失わないようにする。**GitHub側の改名も、このTASKでのPublic/Private変更も実行しない。** 社長の現在の指示は、Public化を先に行い、改名は後日にするというもの。

現行mainの `Catalog.register(old, raw, previews)` は、名称変更時に新しい `Registration` を生成して古いキーを削除するため、履歴・解析結果・取得時刻が失われる。また `StoreActivity.edit` は変更時に旧repoの個別PATを解除する。保存済みAPKのファイルは残るが、出所repoを旧名で記録している可能性も考慮する。

## 実装要件

1. GitHubの安定したrepository IDを優先して改名前後の同一性を確認する。改名を推測で許可せず、旧・新repoが別IDなら移行を拒否して既存データを保持する。旧URLがGitHubのリダイレクトになる場合、API応答・権限・列挙可能性を確かめ、安全に同一性を判断する。ID未取得・旧repoが404・通信断・認証失敗等で同一性を検証できない場合は、**既存情報を消さず**理由と再試行方法を示す。既存登録にIDがない場合の安全な確認・補完経路も設計する。
2. 同一repoと確認できた名称変更では、`Registration` の `history`（全Release履歴）、`inspected`（APK解析結果）、`checked`/`fetched`、更新エラー・状態、`previews`、GitHub ID等を新しいキーへ引き継ぐ。既存の `revision` を参照する非同期更新が旧名へ書き戻したり、新キーに混入したりしないよう、世代管理・競合・処理中キャンセルを考慮する。rename実行中にアプリが終了しても、旧・新の登録が不整合にならないよう原子的または復旧可能な保存手順を採る。
3. 共通PATは既存設定を維持する。個別PATは `StoredAuth` のrepo名依存KeyStore aliasと暗号化保存先を踏まえて、**旧認証が正常に読めること、改名後の保存・復号が成功したことを確認してから**旧エントリを削除する。途中失敗時は旧認証を残し、利用者に再認証が必要か明確に示す。PATをログ・画面・例外・PR・テスト記録へ出さない。
4. `SavedShelf` 内の保存済みAPKとその履歴・出所情報を壊さない。出所repoが名称変更に依存するなら、参照を移行するか旧名と新名の対応関係で引けるようにする。APK本体・署名・packageName・versionCodeは変更しない。自動削除、再ダウンロード、再インストール、端末アプリデータ初期化を伴わせない。
5. 変更先repoが既に別登録されているときは、内容を黙って上書き・破棄・二重登録しない。同一GitHub IDと確認できた場合のみ履歴と解析結果の安全な重複排除・統合を検討し、衝突時は双方を保持して明示的に解決できるようにする。異なるIDなら移行を拒否する。
6. UIの「登録を編集」から操作できること。改名と通常の登録追加・プレリリース設定変更を区別し、移行できた内容と、ID未検証・認証移行失敗等で保留した理由を表示する。必要な場合はGitHub上の現在名を示す。改名前の登録が端末に残っていても勝手に消さない。
7. 共通PATによる自動登録PR #4と併用した際、新名称の再取得で旧名称が二重追加されず、名前の追跡が可能なこと。公開repoも対象となり得る。**Public/PrivateやAPK配布履歴による自動登録フィルタはPR #4側の別課題**とし、本TASKに無関係な機能を混ぜない。
8. `xiaqui/artifact` → `xiaqui/release-store` は実例としてテストするが、特定の2名称にハードコードせず、任意のowner/repo改名・所有者移管で正しく動く範囲と制約を明示する。GitHub APIの制約で安全に移行できないケースは、破壊的な推測移行をしない。
9. Android 6/API23以降の既存互換性、Release取得、更新判定、登録削除、外部Intent経路、APK保管上限、署名検査を維持する。UI追加は最小限にする。

## テスト・検収

- 旧IDあり/なし、旧→新リダイレクト、同一ID/別ID、404/401/403/429/通信断、登録変更中の中断・再起動。
- 既存履歴、解析済みAPK情報、取得時刻、プレリリース設定、共通PAT、個別PATをそれぞれ移行前後に比較する。KeyStore移行失敗でも旧資格情報が消えないこと。
- APK保存済み、端末インストール済み、同じIDで新旧登録重複、異IDの同名衝突、更新確認中の改名、PAT自動登録との重複防止。
- 単体・必要なAndroid計装テスト、lint、CI、独立レビュー、P0/P1修正。Android 6と10のAPI境界を重点確認する。端末でしか分からない操作感は実機検収待ちとする。

## Workへの実行指示・Git運用

1. `xiaqui/rin` の最新main README/STYLEなど共通指示、`xiaqui/artifact` の最新main・AGENTS.md・TASK.md・README.md・関連docs・既存PRを確認する。GitHubの現在状態を正本とし、既存実装やPRとの重複を最初に調べる。
2. **PR #6（自動更新）、PR #4（PAT自動登録）、PR #5（スクリーンショット）は別タスク**。そのbranchを変更したり、勝手にmergeしたりしない。同目的の既存PRがない場合は最新mainから専用branchを作る。PR #6にrename追跡の一般的な記述があっても、既存データの完全移行が実装済みかをコードで判定する。
3. 上記範囲を実装し、テスト・lint・CI・独立レビュー・指摘修正まで自走する。署名鍵・Secrets・PATを表示・出力しない。公開リポジトリなのでActionsを使えるが、文書更新だけでAPKを作らず、同一版Releaseの乱造を避ける。
4. 完了時はPRと検証結果、保存情報の移行前後、既存版への上書き互換性、実機検収項目、未解決リスクを報告する。**社長の実機検収前にmergeしない。** APKが必要なら、版・署名・source SHAを照合した必要最小限の検収用Releaseだけ配送する。

## 非目標

- GitHubリポジトリ自体のrename・visibility変更。
- 既存Git履歴やReleaseタグ/Assetの書き換え。
- PR #4の公開/非公開フィルタ実装、PR #6の自動更新機能の再実装。
- OSのアプリデータやインストール済みAPKの無人移行。
